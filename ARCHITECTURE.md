# Архитектура MVP

Задача: обработать загруженные TXT и выдать действующие условия с проверяемыми источниками. Репозиторий публичный, документы в documents/ — только синтетические.

## Основной путь

Browser File API → src/engine.mjs parseDocument() → классификация (договор/подписанное допсоглашение/проект/письмо) → группировка по номеру договора → применение только подписанных изменений с effective <= asOf → React-free UI → точная строка файла.

**Модель данных:** Document(name,id,kind,signed,effective,lines); Field(value,evidence{file,line,quote},changedBy); Contract(id,supplier,amount,deadline,proposals,review,documents).

Суммы из аванса и лимитов не считаются суммой договора. Даты оплаты не считаются сроком поставки. Письма и проекты не изменяют условия. Не найденные поля = null. Неопределённость = review.

## Размещение

GitHub Pages отдаёт HTML/CSS/JS. GitHub Actions исполняет тесты и публикует статический сайт. Обработка пользовательских TXT остаётся локально в браузере: отсутствуют платные API, постоянный сервер и секреты.

**Ограничение:** GitHub Actions не работает как постоянно доступный HTTP backend и не может напрямую обслуживать вебхуки. Чтобы пользователи запускали асинхронную модель через webhook, нужна постоянно запущенная n8n-инстанция или другой API шлюз. Только она безопасно хранит GitHub credential, делает workflow_dispatch и выдаёт jobId, а UI опрашивает статус через защищённый endpoint. Эта опция НЕ входит в MVP.

**Опциональная модель:** небольшой CPU классификатор/NER в отдельном workflow_dispatch; предсказания являются только кандидатами, каждую цитату необходимо сопоставить с оригинальной строкой; юридические правила и статус остаются детерминированными. Нет необходимости запускать модель ради шести TXT.

**При масштабировании до 100 000 документов:** отдельные API, очередь задач, object storage, PostgreSQL (идентификаторы, версии, поля, права), worker pool, RBAC/ABAC, аудит действий, кеши и выборочный LLM fallback. GitHub Actions оставляется CI/CD, а не пользовательским backend.
