# Semantic TextNavigator — Supply Contract Checker

**Действующие условия договоров поставки с проверяемыми цитатами.** Учебный MVP для специалиста по закупкам: загрузить несколько TXT, получить реестр, открыть первоисточник для каждой суммы и даты, увидеть подписанные изменения отдельно от предложений.

[Открыть приложение](https://tim8es.github.io/supply-contract-checker/) · [Код](https://github.com/tim8es/supply-contract-checker) · [Архитектура](ARCHITECTURE.md) · [Интеграции](docs/integration.md) · [QA](docs/qa.md) · [10-минутная демонстрация](docs/demo.md) · [AI Fallback с личным ключом](docs/ai-fallback.md)

> Для демонстрации откройте страницу с параметром `?demo=1` — учебные TXT загрузятся автоматически. В рабочем интерфейсе можно загрузить другой комплект файлов без API-ключей.

**Для проверки ИИ:** нажмите **«Пример для ИИ» рядом с «Открыть пример»**
в блоке загрузки либо откройте [AI-демонстрацию](https://tim8es.github.io/supply-contract-checker/?ai-demo=1).
Отдельно загрузятся **четыре развёрнутых договора поставки и два связанных документа**:
с промышленным оборудованием, медицинским оснащением, офисной мебелью
и лабораторными расходниками. В них есть цены, сроки, реквизиты,
приёмка, ответственность, подписанное допсоглашение и предложение из письма.
Часть условий распознаётся локально, часть требует **«Проверить через ИИ»**
прямо в реестре, а отсутствующую в приложении цену ИИ не должен придумывать.
Все договоры **реалистично оформленные, но вымышленные**, а исходный набор
из шести файлов STN-101/102/103 и его контрольные ответы сохранены без изменений.

## Запуск

**Без платных API, аккаунтов моделей, базы данных и npm-зависимостей.**

- Требуется браузер с поддержкой ES-модулей. Для тестов и CLI — Node.js **22+**.
- Локальный UI: `python3 -m http.server 8080`, затем `http://localhost:8080`.
- Тесты: `npm test`.
- Отдельный benchmark: `npm run benchmark` (все неудачные случаи в отчёте, **не блокирует** CI).
- Пакетный JSON-вывод: `npm run analyze:demo` или
  `node scripts/analyze.mjs --input documents --date 2026-03-10 --output out/report.json`.
- Для дополнительного поля «Неустойка / день»: добавьте `--with-penalty` к CLI. В интерфейсе поле доступно сразу.
- Публикация: GitHub Pages, Source = **GitHub Actions**. На каждом push в `main` workflow [Test and publish](.github/workflows/ci-pages.yml) сначала проверяет движок и UI в Chrome, затем публикует статический сайт.
- Отдельный workflow [Analyze synthetic contract batch](.github/workflows/batch-analyze.yml) запускается вручную и выдаёт JSON-артефакт для дальнейшего импорта. Он использует **только документы, закоммиченные в репозиторий**.

Использование: «Добавить TXT» → выбрать несколько файлов → установить дату проверки → таблица. Ссылка «Проверить источник» раскрывает точную цитату, её файл и строку, а также **историю значений**: исходное условие → подписанные изменения → действующее значение. Если подписанное изменение невозможно надёжно извлечь, старое значение скрывается, а исходный абзац причины доступен через «Почему нет данных?». Чтобы ответить на четвёртый вопрос, укажите в фильтре **«Срок поставки строго до»** дату 01.04.2026. Дата выбирается пользователем, а не зашита в алгоритм. Блок предложений показывает несогласованные изменения. «Экспорт JSON» сохраняет результаты локально.

## Настраиваемые фильтры по датам и независимая прокрутка источников

В реестре **«Действующие условия»** расположены два независимых поля:
**«Дата актуальности условий»** определяет, какие условия действовали
на выбранный день, а **«Срок поставки строго до»** показывает только
договоры со сроком исполнения *раньше* введённого порога. Пустое поле
срока означает отсутствие фильтра; **«Сбросить срок»** возвращает все
договоры, не меняя дату актуальности. Фильтр по сроку совместим
с вкладками «Все» и «На проверку», а также с поиском по поставщику.
Выпадающий срок не влияет на юридическую применимость допсоглашений.
Для контрольного четвёртого вопроса выберите 01.04.2026; другой
порог можно установить в любой момент без изменений исходного кода.

Поле **«Дата актуальности условий»** задаёт исторический момент, на который
проверяются действующие условия. При изменении даты весь комплект
загруженных TXT **анализируется заново**; исходный договор и подписанные
допсоглашения допускаются только при подтверждённой дате подписания,
не позднее выбранной даты. Для допсоглашения также обязательна дата
вступления в силу не позднее выбранной даты. Письмо или неподписанный
проект не меняют договор даже после своей даты. Имена файлов и дата
загрузки никогда не являются основанием для приоритета.

**Пример STN-101:** 28.02.2026 → 1 200 000 ₽ и 15.04.2026;
10.03.2026 → 1 380 000 ₽ и 30.04.2026.
До подписания основного договора он не показывается как подтверждённый.
Значения, извлечённые AI Fallback, при изменении даты сбрасываются и
не подменяют исторические правила.

На исходном кейсе дата проверки должна быть **10.03.2026** — это
начальное значение поля, которое пользователь может изменить.
Срок поставки **не ограничен по умолчанию**. Если выбрать 01.04.2026,
приложение сравнит действующий срок каждого договора с выбранным
порогом, не изменяя дату проверки. Письма и проекты
отображаются как несогласованные сведения, в том числе если их собственная
дата позже выбранного исторического момента; прототип **не реализует
полноценное восстановление состава корреспонденции на произвольную дату**.

На **широком экране (от 1101 px)** правая колонка с
«ИСТОЧНИК И ДОКАЗАТЕЛЬСТВО» и «ОРИГИНАЛЬНЫЙ ТЕКСТ» закрепляется
относительно окна. У обоих блоков **одна общая вертикальная прокрутка
внутри правой колонки**, независимая от общей страницы:
инспектор цитат **полностью развёрнут по высоте, без внутреннего скролла**,
и исходный TXT **тоже без собственного скролла**. При прокрутке правой
колонки два блока перемещаются вместе; закреплённой остаётся **колонка,
а не сам инспектор**. **«↗ Проверить источник»** всегда показывает
инспектор в начале правой колонки, даже если она была прокручена вниз,
**не переключая оригинальный TXT**. **«Показать в исходном тексте ↗»**
открывает нужный файл, подсвечивает конкретный абзац и прокручивает
общую правую колонку до цитаты, а не до списка файлов.
На планшете/телефоне оба блока отображаются полностью в обычном потоке
страницы и прокручиваются вместе с ней.
Поддерживается прокрутка правой области с клавиатуры.

| STN-102 | ООО «Контур Электро» | **840 000 ₽** | **20.03.2026** | Письмо предлагает 27.03.2026, но изменение не подписано |

## Логика решения

```text
TXT → строки и абзацы → тип документа и номер договора
  → кандидаты суммы/срока с оригинальным span
  → привязка документов по номеру
  → проверка: подпись + дата подписания + дата вступления в силу
  → разрешение конфликтов и неопределённости
  → реестр + предложения + цитаты + JSON
```

Данные: `Document` (name, id, kind, signature, signedAt, effective, blocks); `Field` (value, evidence{file,line,endLine,quote}, changedBy, effective); `Contract` (id, supplier, amount, deadline, proposals, review, documents).

Система **не предполагает, что упоминание суммы означает цену договора**: авансы, бюджеты и штрафы игнорируются; суммы из отсутствующих спецификаций не выдумываются. Для изменения нужны явный статус подписания сторонами, дата подписания не позднее даты проверки и дата вступления в силу не позднее даты проверки. Письма и неподписанные проекты отражаются отдельно. Противоречащие основания, дубликаты и неопределённость приводят к «Нет данных» / «На проверку», а не к случайному выбору. Переходы «с X на Y» извлекают **новое** значение в том числе для подписанного соглашения; если соглашение явно меняет сумму или срок, но новое значение неизвестно, старое нельзя считать подтверждённым. Следующее вступившее в силу однозначное соглашение может восстановить подтверждённое поле.

Используется небольшой набор расширяемых языковых правил, а не LLM: это быстрее, воспроизводимо и не требует внешней инфраструктуры. **Это не универсальный юридический NLP**: новые фразы за пределами правил могут не распознаться. Подтверждение подлинности подписи отсутствует — обрабатывается только текст статуса. Подробнее: [ARCHITECTURE.md](ARCHITECTURE.md).

## Необязательная проверка пропущенных полей через ИИ

В таблице **«Действующие условия»** рядом с **каждым «Нет данных»**
(сумма, срок поставки, ставка неустойки) появляется кнопка
**«✦ Проверить через ИИ»**. Нажатие отправляет в выбранный API
только относящиеся к договору и выбранному полю разрешённые исходные абзацы.
Ответ отображается в **той же ячейке** с меткой «ИИ · проверить»
и переходом к точной цитате. При неподписанных договорах, дубликатах и
противоречиях найденный фрагмент показывается для ручной проверки,
**но не становится действующим условием**. Отсутствие данных и ошибка API
тоже объясняются прямо в ячейке.

Кнопка **«↗ Проверить источник»** раскрывает цитату в блоке
**«ИСТОЧНИК И ДОКАЗАТЕЛЬСТВО»**, не переключая исходный документ и не
прокручивая страницу к оригиналу. Переход к полному TXT — отдельная
кнопка внутри инспектора.

**Настройки** расположены непосредственно в реестре — «⚙ Настройки ИИ».
Endpoint и модель автоматически сохраняются **локально в браузере**
(`localStorage`) и восстанавливаются после перезагрузки. **API-ключ
сохраняется только после отдельного согласия** («Сохранять API-ключ
на этом устройстве»), в незашифрованном виде. На общем компьютере
этот флажок включать нельзя. Кнопка удаления очищает настройки, ключ
и кандидатов модели.

**[Пример специально для AI](https://tim8es.github.io/supply-contract-checker/?ai-demo=1)**:
четыре отдельных договора, подписанное допсоглашение и письмо-предложение.
Набор находится только в папке [examples](examples/) и не смешивается
с первоначальными шестью документами. Локальный парсер должен пропустить
часть нестандартных формулировок, а модель может предложить значения
**с точными цитатами**, если модель корректно понимает договор. Один из
договоров намеренно ссылается на не приложенную спецификацию — корректный
результат для его суммы остаётся «Нет данных».

Сервер/API-ключ не обязателен для работы приложения и CI. API-провайдер
должен разрешать CORS. Платные запросы и передача текста внешнему API
выполняются только по кнопке пользователя; не загружайте конфиденциальные
договоры без разрешения. Модель не определяет статус подписания и не
заменяет юридические правила. Протестирована работа с mock API,
не точность конкретной модели. Подробности: [docs/ai-fallback.md](docs/ai-fallback.md).

## Независимая оценка качества и расширяемости

Создан отдельный синтетический [holdout из 36 сценариев](benchmark/holdout.mjs) с **72 эталонными полями**, не совпадающий с шестью исходными документами. Зафиксированный [первый отчёт](benchmark/BASELINE.md): **precision 100%, recall 84,21%, ложных действующих значений 0, пропусков 9**. После дополнительного аудита контекста оплаты, поставки и цены с авансом: **precision 100%, recall 85,96%, ошибочных действующих значений 0, пропусков 8** на том же синтетическом наборе (см. [сравнение](benchmark/CONTEXT_AUDIT.md)). Новые правила были проверены на этом корпусе; он уже не является независимой контрольной выборкой для последующих улучшений. Считаются также точность цитаты и совпадение числового токена с исходным текстом. Результат ограничен синтетическими сценариями: **это не доказательство качества на реальных договорах**. Ошибки видны в benchmark и не скрываются после расширения правил.

Каждый результат проходит дополнительную проверку источника: имя файла, дословный диапазон строк, исходный токен и соответствующее ему значение. Верификатор не утверждает юридическую силу документа — это отдельная ответственность правил подписания и срока действия.

**Расширение без переписывания правил:** независимый модуль [`src/extractors/penalty.mjs`](src/extractors/penalty.mjs) добавляет **ставку неустойки в процентах за день**. Для оригинальных TXT: STN-101 — **0,1%/день**, STN-102 — **0,05%/день**, STN-103 — **нет данных**. Он использует тот же механизм подписи, даты, истории и цитат. Максимальный предел неустойки не путается с ежедневной ставкой. Поле показано в интерфейсе и доступно в JSON/CLI.

## Продуктовая записка (для обсуждения с заказчиком)

**Кто пользуется и зачем.** Специалист по закупкам за минуты сверяет условия партии договоров, не перечитывая весь комплект; каждое значение проверяет переходом к первоисточнику. Система не выносит юридическое заключение, а ускоряет контролируемую проверку.

**Пять вопросов клиенту перед развитием:**
1. Какие реальные шаблоны/форматы, языки и объёмы документов встречаются?
2. Где хранится подтверждение подписи, даты подписания и юридической силы изменения?
3. Какие виды условий нужно проверять после суммы и срока (неустойка, НДС, графики, спецификации)?
4. Когда результат должен блокироваться до проверки человеком; кто и как утверждает исправления?
5. Какие нужны источники интеграции, роли пользователей, права доступа и сроки хранения?

**Допущения:** небольшие UTF-8 TXT; один основной договор на номер; номер присутствует в тексте; явные статусы и даты; русскоязычные формулировки из ограниченного, тестируемого набора; календарная дата по стандартной системе без рабочих дней и часовых поясов; компании и условия вымышлены.

**Две метрики:**
- **Document-grounded field accuracy:** доля полей, у которых и значение, и цитата корректны на размеченной тестовой выборке; цель ≥95% на согласованном наборе (гипотеза, не достигнутая производственная метрика).
- **Время сверки:** медианное время от загрузки до подтверждения закупщиком суммы и срока по одному договору; цель <30 секунд/договор и сравнение с контрольным ручным сценарием (пока не измерено).

**Три ключевых решения и их компромиссы:**
1. Детерминированные правила → объяснимость, нулевая стоимость инференса, но ограниченные формулировки.
2. Извлечение и применение юридических правил разнесены → проще проверять и расширять, но больше явно описанных состояний неопределённости.
3. Browser-first + Pages/Actions → нет постоянного сервера, загруженные документы остаются в браузере; минусы — нет общей истории, пользовательских ролей и синхронных вебхуков.

**Что изменится при 100 000 документов и правах доступа:** ingestion API, очередь, object storage с версиями, реляционная БД (договоры, связи, источники, решения человека), полнотекстовый индекс, фоновые воркеры, RBAC/ABAC вплоть до документа и фрагмента, аудит изменений и observability. Actions остаётся CI/CD; он не является интерактивным backend.

**Три следующих улучшения в порядке приоритета:** (1) корпус реальных обезличенных формулировок, benchmark и управляемое расширение extractor rules / fallback модели; (2) человеческая верификация, история решений и сохранение проверок; (3) защищённый API и коннекторы к ЭДО/ERP с контролем доступа.

## Краткий отчёт о вайбкодинге

**Инструмент:** GPT-6 (ChatGPT) + GitHub connector + GitHub Actions CI. Разработанные AI-код и гипотезы проверяются воспроизводимыми автоматическими тестами и снимком Chrome, а не принимаются «на веру».

**Примеры запросов к ИИ:**
- «Перепиши анализ документов так, чтобы извлечение полей было отдельно от проверки статуса и даты, каждое поле хранило дословный исходный абзац».
- «Придумай негативные тесты: дубликаты договоров, две разные цены, неподписанное соглашение, письмо, бюджетный лимит, договор с новой формулировкой».
- «Сделай B2B интерфейс для закупщика без тяжёлого фронтенд-стека, с инспектором цитат и удобной таблицей».

**Ошибка AI и исправление:** в первой переработке парсер принял дату подписи за срок поставки в договоре без пустых строк между полями. Это обнаружил регрессионный тест нового договора (ожидалось 19.03.2026, фактически возвращалось 10.03.2026). Исправлено разделение абзацев по семантическим границам, после чего CI прошёл. Более поздние изменения проверяются дополнительными негативными сценариями.

**Затраты времени (оценка по рабочим окнам; без отдельного таймера):** исходный прототип — около 40 минут; профессиональная переработка — около 40 минут; усиление юридической корректности — около 15–20 минут; независимый синтетический benchmark, верификатор источников и подключаемый extractor — около 15–20 минут (коммиты 06.11.2026 01:38–01:53 МСК); дополнительный аудит привязки дат к условиям и денежных сумм в одном абзаце — ориентировочно 10–15 минут. **Суммарно ориентировочно 3 часа 10 минут — 3 часа 40 минут активной разработки**, включая BYOK AI fallback, точечные кнопки в реестре, сохранение настроек модели и проверку CI (оценка по коммитам, без таймера) из допустимых четырёх, без простоев. Это оценка: Git фиксирует коммиты, но не полный хронометраж анализа и локальных проверок. Последующие изменения интерфейса и расширение учебного набора выполнены по дополнительным запросам после первоначальной сдачи; их нельзя считать частью исходной четырёхчасовой оценки без дополнительного хронометража.

**Оставшиеся задачи:** (1) разметить корпус реальных обезличенных договоров и измерить точность на неизвестных форматах (синтетический корпус из 24 вариаций уже добавлен, но он не заменяет реальные документы); (2) подтверждение подлинности подписей и сохранение человеческих решений; (3) защищённые хранилище, роли и интеграции для корпоративного использования. Эти функции **не входят в текущий MVP**.

## Ограничения и безопасность

- Только TXT, без PDF/DOCX/OCR; нет цифровой проверки подписей, внешнего юридического реестра и выполнения произвольных запросов к LLM.
- Фразы, сложные относительные/рабочие сроки, расписания по спецификациям и ряд юридических конструкций не поддерживаются. В неоднозначной ситуации требуется специалист.
- В браузере нет регистрации, постоянного сохранения, истории исправлений или разграничения доступа; обновление страницы очищает пользовательские данные.
- **Не коммитьте реальные конфиденциальные договоры в публичный репозиторий.** Клиентская загрузка через интерфейс остаётся локальной; пакетный Actions workflow читает только файлы из Git.
- **Регрессионная проверка:** 153 автоматических теста, включая mock AI API и 24 независимых положительных и отрицательных сценария формулировок, ошибки «с X на Y», неопределённые вступившие в силу изменения и историю источников. Тесты — защита известных случаев, **не доказательство качества на любых договорах**.
