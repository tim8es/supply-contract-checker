# Supply Contract Checker — Semantic TextNavigator MVP

Учебный прототип для закупщика: загрузка нескольких русскоязычных TXT, таблица действующих сумм и сроков поставки на выбранную дату, дословные цитаты и переходы к исходным строкам. Приложение не использует платный API, LLM и сервер для загрузки пользовательских документов.

## Установка, запуск, использование

**Требования:** современный браузер; Node.js >= 20 только для тестов. npm-зависимостей нет.

1. Клонируйте репозиторий. Запустите тесты командой `npm test`.
2. Запустите локальный HTTP-сервер в корне репозитория: `python3 -m http.server 8080`.
3. Откройте `http://localhost:8080`. Выберите сразу несколько TXT или нажмите «Загрузить учебные документы».
4. Дата по умолчанию — 10.03.2026. Сумма и срок содержат ссылки на исходное имя файла и строку. Кнопка «Поставка до 01.04.2026» отвечает на четвёртый контрольный вопрос.
5. Для публикации: **Settings → Pages → Build and deployment → Source: GitHub Actions**. После настройки повторно запустите workflow «Test and publish».

## Архитектура

```text
File API → Document parse/classify → Extract field + exact line
         → Link by contract ID → Apply effective signed amendments
         → Result + evidence → Table / Source viewer
```

**Модель:** Document {name, id, kind, signed, effective, lines}; Field {value, evidence:{file,line,quote}, changedBy}; Contract {id, supplier, amount, deadline, proposals, review, documents}. Отсутствующие сведения представлены `null`, в UI отображаются «Нет данных». Несогласованные предложения сохраняются отдельно; условия меняет только явно подписанное допсоглашение, вступившее в силу к дате проверки.

- `src/engine.mjs` — чистые функции без DOM и сетевых запросов. Цитата хранится **дословно** вместе с именем файла и номером строки. Дата документа или имя файла не используются для приоритета.
- `src/app.mjs` — UI без фреймворка, клиентская обработка пользовательского TXT, таблица, переход к исходной строке, фильтр.
- `.github/workflows/ci-pages.yml` — тесты на Node.js 22 и публикация статического сайта. GitHub Actions не заменяет постоянно работающий backend; пользовательские файлы не передаются в CI.

**Три технических решения и компромиссы.** 1) Детерминированный парсер вместо LLM: дешево, быстро, воспроизводимо, но поддерживает лишь ограниченный набор формулировок. 2) Браузер как compute: нет backend, токенов и передачи документов, но нет совместной истории и фоновой обработки. 3) GitHub Pages + Actions: минимальное обслуживание, но нет входящего вебхука/синхронного API, а Pages требуется включить один раз.

**n8n — необязательное расширение.** Если нужен внешний webhook, n8n необходимо хостить отдельно, постоянно. Он должен принимать защищённый POST, передавать задание в Actions через `workflow_dispatch` с серверными GitHub credentials, возвращать job ID и предоставлять проверку статуса. Без n8n/другого API-шлюза **нельзя безопасно запускать GitHub Actions из публичного браузера**: токен нельзя хранить в клиентском коде. Для шести TXT такой путь создаёт задержки и не нужен.

### Краткая записка для Product Owner

**Пользователь:** специалист по закупкам, проверяющий действующие условия без прочтения полного пакета документов.

**Пять вопросов клиенту:** (1) Какие реальные форматы и шаблоны используются? (2) Как подтверждаются подписи и вступление изменений в силу? (3) Какие условия важнее суммы и срока? (4) Какие ошибки критичны и как организовать ручную верификацию? (5) Какие правила доступа/хранения необходимы?

**Допущения:** русскоязычные UTF-8 TXT знакомой структуры; статус подписания записан текстом; идентификатор договора указан явно; дата вступления в силу у допсоглашения явная; нет самостоятельной юридической проверки подлинности подписей.

**Две метрики:** (1) доля правильно определённых полей с точной проверяемой цитатой, цель ≥95% на согласованном контрольном наборе; (2) медианное время нахождения и ручного подтверждения условия, цель <30 секунд и сравнение с ручным чтением. Цели — гипотезы, не измеренные достижения.

**При 100 000 документах и правах доступа:** потребуется перейти к API ingestion, очереди фоновых задач, объектному хранилищу файлов, PostgreSQL для полей и версий, RBAC/ABAC, аудиту прав и событий, индексации по договорам, мониторингу извлечения. GitHub Actions оставить CI/CD, не сервером интерактивных запросов.

**Следующие улучшения (по приоритету):** (1) покрыть дополнительные реальные формулировки, конфликты и статусы тестами; (2) ручная верификация с сохранением решений; (3) опциональная малая модель/LLM fallback для неоднозначных документов с обязательной проверкой ссылок на исходник.

### Vibe coding / ИИ

**Инструмент:** ChatGPT GPT-6 для архитектуры, генерации функций, тестов и диагностики Actions.

**Характерные запросы:** «Напиши минимальный детерминированный парсер и не используй имена файлов как правило»; «Раздели подписанное вступившее в силу допсоглашение и несогласованное письмо/проект»; «Добавь тест нового договора с изменёнными суммой, датой и номером».

**Ошибка и исправление:** первоначальный шаблон `/^письмо\b/iu` в JS не распознавал кириллическое слово из-за особенностей `\b`. Замена на `/^письмо(?:\s|$)/iu`; повторный запуск тестов подтвердил правильную классификацию. Отдельно выявлена проблема CI deployment: GitHub Pages не активирован в настройках репозитория, а тесты проходят.

## Известные ограничения и безопасность

Только TXT, небольшие документы, ограниченные формулировки. Подписи не проверяются криптографически; извлечение не равно юридическому заключению. Не все возможные юридические конфликты определяются автоматически: сомнительные случаи должны передаваться человеку. Нет PDF/OCR, хранения, пользователей, доступов, произвольного чата и production-мониторинга. При обновлении страницы загруженные данные исчезают. В публичном репозитории только вымышленные учебные документы; настоящие договоры в git коммитить нельзя.

**Завершение и оставшиеся задачи:** код, автоматические тесты и CI созданы; публикация в Pages требует ручного включения Pages, затем smoke-test в браузере и проверка на дополнительных шаблонах. Фактический срок сессии разработки следует фиксировать по своему таймеру; Git-коммиты не эквивалентны достоверному учёту всех трудозатрат.
